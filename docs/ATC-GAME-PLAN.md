# 空管游戏 v1 方案（从零重写）

> 2026-10-18 · 状态：待 zz 评审

## 0. 决策摘要

| 项目 | 决定 |
|---|---|
| 品类 | 全席位、全流程机场管制（空中 + 地面），中等拟真、操作简化 |
| 平台 | 浏览器，零安装，桌面优先（≥1280×720） |
| 技术栈 | TypeScript + Vite；3D 用 three.js；UI 层用 React（理由见 §5.3） |
| 产品形态 | **浮动窗口工作台**叠在 3D 视景上，不是固定 HUD |
| 核心资源约束 | 跑道是唯一互斥资源，地面是瓶颈 —— 一切张力来自"排序" |
| 单局结构 | 关卡制「班次」（60 游戏分钟），班末评级；后续再加无尽模式 |
| 首个机场 | 虚构机场（数据驱动，可扩展），不追真实机场 1:1 |
| 明确不做 | 语音识别、多人、真实涂装、完整飞行力学、移动端、1:1 建模 |
| 交付顺序 | **3D 与玩法一体做**（2026-10-18 决定，推翻原"先 2D 后 3D"）：第一版就是 3D 主视图，2D 只保留一张辅助地面图 |
| 首个交付 | 一个可完整值守的班次：进场落地 + 离场起飞全链路，含 2 个关卡 |

## 1. 从视频里读出的三件事（决定方案走向）

我把两段视频逐 3–5 秒抽帧看完了。以下结论都带画面证据，不是推测。

### 1.1 产品本体是工作台，3D 是背景板

实机画面里，屏幕上同时存在 6 类浮动窗口，全部可拖动、可缩放，甚至有「进入窗口编辑模式」：

| 窗口 | 内容 | 证据 |
|---|---|---|
| 地面滑行图 | 机场平面图、飞机图标、滑行道编号（H2/H9/H10…）、蓝/红道面标记、拖拽画路线 | 实机 00:15 / 00:20 |
| 空域雷达 | 黑色底、飞机标签（呼号+高度+趋势）、距离环，缩到很小仍可用 | 实机 00:50 右上 |
| 无线电记录 | `[09:45:38] [GND] → [UAL8844]` 双向逐条，含频率移交 | 实机 00:55 左下 |
| 航班列表 | 按席位分组（GND / TWR / APP 三个按钮带计数），每架一张卡，颜色编码 | 实机右下 |
| 指令条 | 选中飞机后底部弹出 2–4 个**管制用语**选项 | 实机 00:20「执行复飞 / 取消降落许可 / 选择出口」 |
| 飞机信息卡 | 呼号、机型、计划/实际时刻、机位、跑道、状态、距离、地速、高度 | 实机底部中央 |

中间那块 3D 视景里，飞机只是带一个青色标签的剪影。**玩家 90% 的操作发生在窗口里，3D 负责"我在机场"的空间感与情绪。** 这跟我们之前把它当"主视图"的思路正好相反。

### 1.2 一半玩法在地面，且地面才是瓶颈

实机里的完整链路：批准推出（要选机头朝南/朝北）→ 在地面图上**画滑行路线**（卡牌显示路线串 `N_B_A_A14`）→ 跟在前机后 / 暂停滑行 / 等待滑行 / 穿越跑道 → 跑道外等待 → 可以起飞（复诵风向风速）→ 起飞 → 移交离场。落地反向：选脱离口（如 B3 高速口）→ 等前机通过 → 联系地面 → 滑到机位。

地面段之所以好玩，不是"多了个环节"，而是它把**跑道从"空中飞机的落点"变成了"全场唯一的共享资源"**：落地、起飞、穿越三条需求在同一根道面上抢，排序决策才有代价。

### 1.3 指令条是"玩家的语言"，不是表单

选项文案本身就是管制用语：`执行复飞`、`可以推出开车，机头朝南`、`B3 脱离`、`跑道外等待`。玩家读选项的过程等于学术语，这是这类游戏"像在管制"的最大来源，且零成本（纯 UI + 状态机映射）。

> **对旧方案的修正**：旧文档把"3D 塔台 + 2D 雷达双视角"当护城河，这是错的（Tower!3、Unmatched ATC 都是标配）。真正难做且构成体验差异的是 **工作台 + 情境化指令 + 地面域**，这三样都不需要高美术投入。

## 2. 定位与不做什么

**一句话**：打开网页就能管的机场 —— 看得见飞机起降，不用背术语，但机制不打折。

- 目标人群：好奇但没入门的大多数；硬核玩家留给 Endless ATC，不去抢。
- 差异化：Web 零门槛 × 全流程（含地面）× 工作台式操作。品类里 PC/移动都已被占满，Web 端没有成熟的全流程产品。
- 品类天花板要认：Endless ATC 97% 好评但 Steam 月活 12–15 人。这是作品集/内部玩具级题材，不是商业项目。

**不做**：语音识别与 TTS 喊话（Tower!3 的死穴）、货币化解锁（UATC 的差评来源）、1:1 设施与真实涂装（AC27 的地盘）、完整飞行力学、多人协同、移动端适配。

## 3. 玩法设计

### 3.1 一局是什么

一局 = **一个班次**，60 游戏分钟，开局给出本班次的航班表（到港/离港各若干，带计划时刻），玩家从早班静场跑到高峰。

| 要素 | 设计 |
|---|---|
| 时间 | 1x = 每 10 现实秒走 1 游戏分钟（60 分钟班次 ≈ 10 现实分钟）；可 1/2/4/8 倍速、可暂停 |
| 结束 | 班次时钟走完，按"处理架次 + 违规"评级 S/A/B/C |
| 关卡 | 5 个班次逐级加量：① 1 架落地 ② 3 架混合 ③ 地面开始拥堵 ④ 风变→换跑道 ⑤ 双跑道高峰 |
| 随机性 | 航班表由种子生成，天气/流控扰动小范围随机；同一种子必复现（便于回放与调参） |
| 失败 | 不设硬失败，只有评级下滑；跑错跑道、间隔丢失、跑道侵入各记违规 |

> 关卡制而不是无尽模式：班次有开头有结尾，评级有落差，才有人愿意再打一遍。无尽模式作为第 6 关之后的解锁项。

### 3.2 核心循环与张力

```
航班表（可预读） → 预排序（谁先落地、谁先走） → 下达指令（无线电复诵有延迟）
        ↑                                              ↓
   评级 / 复盘 ←── 事件（落地、起飞、违规、复飞）←── 世界按 10Hz 演进
```

张力只来自三个地方，全部围绕跑道：

1. **进近排序**：两架同时到，谁先？后机拉长还是盘旋等待？
2. **地面排队**：推出顺序决定谁先到跑道外；前机滑得慢，后机就顶上来
3. **跑道共享**：起飞、落地、穿越三种许可互斥，给了这个就得拒那个

### 3.3 席位与移交

三个席位 **GND / TWR / APP**，玩家一人全管，席位是**视图切换 + 指令分组**，不是三个玩家。

- 移交是玩法不是噪音：进近排序好 → 交塔台 → 塔台给落地 → 落地后交地面 → 地面给脱离口与滑行。移交错了（例如还没落地就交地面）会被飞行员顶回来，扣分但可纠正。
- 每个席位只显示该席位能下的指令，避免"选项太多不知道点哪个"。
- 频率移交在无线电里显式出现（`联系塔台 118.1`），这是"像管制"的重要演出，成本极低。

### 3.4 指令集（按席位）

| 席位 | 指令 |
|---|---|
| **GND** | 可以推出（机头朝 N/S/E/W）· 滑行经（在地面图上画路线，自动补全路点）· 跟随前机 · 暂停滑行 · 继续滑行 · 穿越跑道 · 联系塔台 |
| **TWR** | 进跑道等待 · 可以起飞 · 可以落地 · 复飞 · 从 X 脱离 · 联系地面 · 联系离场 |
| **APP** | 下降到 / 爬升至 · 航向 · 直飞（点航路点）· 速度 · ILS 进近 RWY xx · 等待 · 联系塔台 |
| 通用 | 复诵、驳回（跑道被占时自动说明原因，例如"跑道 18L 上有 XXX"） |

指令模型统一为**纯数据命令 + 校验 + 排队执行**：`{ type, aircraftId, params }` → `validate()` 返回 `ok | reject(reason)` → 进队列 → 2.5 s 后飞行员复诵并生效。这套结构天然支持"驳回要有原因"和"回放重放"。

### 3.5 计分与评级

- 正向：落地 +12（指定跑道 +6）、起飞 +6、按时移交 +2
- 违规：间隔丢失 −15、跑道侵入 −20、复飞 −4、落错跑道 −8、出界 −8
- 评级：按 完成架次 / 违规数 计算，S 需 0 违规且完成率 ≥95%
- **预测级冲突只提示不扣分**（红线：玩家不该为了消警去做无意义动作）

### 3.6 教学

第一关不是教程文本，是**一个只有 1 架飞机的班次**：飞机会自己沿 STAR 飞进来，玩家只需要点「ILS 进近 → 可以落地」。第二关加"下高度"。第三关加"推出+起飞"。术语通过指令条选项自然习得，不做 PDF 手册。

## 4. 机场与数据模型

机场是**纯数据**，加机场 = 加一个数据文件 + 通过校验。

```ts
// 机场数据结构（示意，实际用 zod 定义并校验）
interface Airport {
  id: string; name: string;
  runways: Runway[];              // 跑道几何、入口坐标、ILS、脱离口列表
  taxiways: { nodes: TaxiNode[]; edges: TaxiEdge[] };  // 有向图，边带单向/宽度/最大速度
  stands: Stand[];                // 机位坐标、机头停放朝向、可推出的方向
  fixes: Fix[];                   // 航路点
  procedures: { stars: STAR[]; sids: SID[] };  // 含高度/速度限制
  sectors: Sector[];              // 扇区多边形 + 移交点
}
```

**校验必须在启动时做，失败就报错退出**（这是旧实现绕圈死锁的一类根因）：

- 滑行道图连通性：每个机位都能到每条跑道入口
- 每条跑道都有至少一个脱离口，且脱离口之后能回到滑行道
- STAR 末点与 ILS 航向道的夹角 ≤ 30°，否则飞机截不住
- 跑道与滑行道的交叉点必须显式建模为 `crossing` 节点（否则穿越跑道这条玩法无处附着）

**起步机场**：Kestrel（单跑道 + 6 机位，教学关用）与 Halcyon（双平行跑道 + 16 机位 + 两条平行滑行道，主战场）。虚构而非真实机场：真实机场的航图/程序数据有授权与准确性问题，且几何要为玩法服务（真实机场的滑行道往往长到让玩家等 5 分钟）。

## 5. 技术架构

### 5.1 分层

```
┌─────────────────────────────────────────────┐
│ UI 层（React）                                │
│   工作台窗口：地面图 / 雷达 / 无线电 / 航班条 / 指令条 │
├─────────────────────────────────────────────┤
│ 3D 视景（three.js，命令式，只有一个 mount 点）      │
├─────────────────────────────────────────────┤
│ 输入与命令层：Command → validate → queue         │
├─────────────────────────────────────────────┤
│ Sim Core（纯 TS，零渲染/零 DOM 依赖，10Hz 定步长）    │
│   飞机状态机 · 地面占用 · 冲突 · 交通 · 计分        │
└─────────────────────────────────────────────┘
        单向数据流：Sim 产出只读快照 → UI 消费
```

### 5.2 七条红线（写进 eslint / tsconfig，违反即构建失败）

1. `src/sim/**` 禁止 import `three`、`react`、`src/ui/**`、`src/views/**` —— 用 `eslint-plugin-import` 的 `no-restricted-imports` 锁死
2. sim 层**不出现** kt / ft / NM 字面量，内部一律 SI；格式化只允许在 `format/` 里
3. 所有状态用判别联合（`phase: 'taxi' | 'hold_short' | ...`），禁止用多个 boolean 拼状态
4. 指令条选项必须由 `availableCommands(aircraft, world)` 单一函数产出，UI 里禁止出现 `if (phase === ...)` 决定按钮
5. 确定性：固定步长 + `seed` 随机源；`seed + 指令日志` 必须能重放出逐帧一致的结果
6. 视图只读快照，任何修改世界的动作走 Command
7. 机场数据启动即校验，不合法直接崩，不做"容错"

### 5.3 技术栈选择与理由

| 层 | 选择 | 理由 |
|---|---|---|
| 语言/构建 | TypeScript strict + Vite | 无争议 |
| Sim | 纯 TS，`Map<EntityId, Entity>`，10 Hz | 手写、可测、无框架负担 |
| UI | **React 19 + `useSyncExternalStore`** | 工作台有 6 个浮动窗口、每窗 10Hz 刷新、条件渲染密集。手写 DOM 是旧实现 bug 的主要来源（视图互相踩状态、列表不滚动、选中被误清）。React 的声明式渲染把这类问题一次性消掉，代价只有 ~45 KB |
| 3D | three.js（不用 R3F） | 一个场景、一个循环、一个挂载点，命令式比声明式更好控；也避免 R3F 与 React 生命周期纠缠 |
| 2D 视图 | Canvas 2D + 图论命中检测 | 地面图与雷达共用一套变换/绘制工具；缩放拖拽自己做，坐标换算统一 |
| 测试 | Vitest（单测 + 场景回归） | sim 层可无头跑；回放断言是调参的主要手段 |
| 音频 | WebAudio 合成 | 无线电"咔哒"+ 提示音，不依赖素材与 TTS |

**Sim 是否放 Web Worker**：v1 不放。快照边界已经序列化友好，真的卡了再搬。过早拆 worker 会让调试成本翻倍。

### 5.4 Sim 内核的几个关键设计（直接针对旧实现的失败模式）

| 问题 | 旧实现怎么坏的 | v1 怎么做 |
|---|---|---|
| 航路点跟随 | 用"到点判定 + 提前转弯"两个半径打架，飞机绕点无限盘旋，交通名额被永久吃掉 | 路径按**弧长参数化**，沿折线推进 `s += v·dt`，到点必达；另加"绕圈保护"断言：一架飞机在 5 分钟内未推进 `s` 直接抛错 |
| 交通生成 | 开局预置飞机占满容量上限，生成函数首行 return，从此零生成 | 容量用**显式账本**（`slots: { inUse, reserved, max }`），生成前必须 `reserve()`，释放必须成对；账本不平会打印告警 |
| 指令条门控 | 按钮的显示条件依赖"这条指令执行后才有的状态"，自锁 | 选项由 `availableCommands()` 纯函数产出，并对**所有 phase 做穷举单测**（每个 phase 至少有一组可达选项） |
| 冲突分域 | 地面等待的飞机被当成空中飞机判间隔 | 冲突检测按域拆成 `airConflict` / `groundConflict` / `runwayConflict` 三个模块，各自独立的罚则与提示文案 |
| 单位混用 | 视图里到处 `* 1852`、`/ 0.514444` | 只在 `format/` 出现换算，eslint 禁数字字面量出现在 sim |

### 5.5 地面管制模型（v1 最难的一块，先说清）

- **图**：滑行道 = 有向图。节点类型：`stand`（机位）、`taxi`（普通）、`holding`（跑道外等待）、`exit`（脱离口）、`crossing`（跑道穿越点）、`intersection`（交叉口）。
- **占用**：飞机占用"边 + 前方一段距离"，后机进入同一段前必须先拿到预约；拿不到就自动停在节点前（并在列表里标"等待中"）。玩家可用「跟随前机」放松间距，「暂停滑行」主动让路。
- **推出**：机位 + 机头朝向 → 拖车直线推出 30–40 m → 转自身动力。推出时占用机位周边扇区，后机不能同时推。
- **跑道**：单一互斥资源，状态 `free / landing / takeoff / crossing`。任何许可都要过 `validate`，冲突则驳回并给出原因。这是全游戏最重要的一个锁。
- **滑行速度**：直线 15 kt、转弯 10 kt、机坪 5 kt；玩家可给"快速滑行"（+5 kt，转弯半径变大）。

| **M4** 3D 视景 | 程序化机场几何、低模飞机、塔台/跟机/自由三视角、昼夜与灯光、与 2D 严格同源 | 切视角不丢状态；同一架飞机在 3D 与地面图的相对位置误差 < 5 m；夜晚跑道灯可辨认 | M |

> **M3 就是"可以给人玩"的版本**（纯 2D）。M4 的 3D 是加值不是前置 —— 这条顺序是刻意的：上一轮把 3D 提到最前面，结果玩法链路坏了都没人发现。

## 7. 工程质量纪律（针对"旧代码质量差"）

这一轮质量问题的根因不是"不会写"，而是**没有可执行的约束，且验收靠肉眼**。以下四条必须落地：

1. **验收必须机器化**。每个里程碑的验收标准写成 `npm run accept:mN` 脚本，跑不过就是没过。肉眼在浏览器里点两下不算验收。
2. **回放是唯一调试入口**。报 bug 时提交 `seed + 指令日志`，本地一行命令复现；没有回放就没法调参、没法做回归。
3. **单文件单职责，超过 400 行就拆**。旧实现的 `world.ts` / `aircraft.ts` 都是千行级巨石，改一处牵连三处。
4. **每个工作包一个提交，提交信息写"改了什么 / 怎么验证的"**；`docs/CHANGELOG.md` append-only，新的在最上。

## 8. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 地面域比预期大（滑行道图 + 占用 + 路径 + 穿越） | M2 拖长，整体延期 | 地面模型先做"节点预约 + 单向前进"，不做并行滑行与超越；M2 验收只要求不死锁，不要求高效 |

| React 10Hz 刷新掉帧 | 手感差 | 快照做脏标记 + 只有变化的窗口重渲染；实在不行把雷达/地面图换成 Canvas（本来就是） |
| 机场数据手工成本 | 加机场很贵 | 先只做 2 个机场；数据结构设计成可由 OSM/OurAirports 半自动生成，但不做在 v1 |
| 3D 美术拖垮进度 | 无限打磨 | 全程程序化低模，禁用外部模型资源；M4 给硬上限（2 周量级） |

## 10. 需要 zz 拍板的四件事

1. **真实机场还是虚构机场？** 我建议虚构起步（授权干净、几何为玩法服务），后续再做导入 pipeline。
2. **3D 必须进 v1 吗？** 我建议 M4 做，但承认 3D 是这个题材的"第一眼卖点"——如果目标是对外展示，可以把 M4 提前到 M3 之前，代价是玩法验证延后。
3. **React 还是原生 DOM？** 我建议 React（理由见 §5.3）。如果你更想控制依赖体积，我用原生 + 一个 200 行的响应式渲染器，但要多花时间在 UI 稳定性上。
4. **单局 10 现实分钟够不够？** 班次制 60 游戏分钟是我拍的，可以改成 30 分钟短班次（更适合试玩）或 90 分钟长班次（更有"值班"感）。

### 12.2 与方案的偏差

- **工作台是固定面板，不是浮动窗口**：先保证可玩，浮窗拖拽/布局保存留到后面（`ui/App.tsx` 里每个面板已经是独立组件，改成浮窗不需要动 sim）。
- **席位移交没做**：指令条直接给全部权限，无线电里有席位前缀。移交玩法排在下一批。
- **尾流间隔没接**：间隔只有 3NM/1000ft 的 CPA 判据，没有按机型类别排序。
- **只有一条跑道同时使用**：`runwayOccupantId` 是单值，双跑道并行要改占用模型。
- **2D 雷达没有**：只有一张辅助地面图；进场排序目前靠航班列表的距离列 + 3D 标牌。
