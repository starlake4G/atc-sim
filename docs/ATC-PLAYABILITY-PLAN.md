# Kestrel Approach：差距分析与可玩性改造计划

2026-10-18。用户要求：对照 refs 两段视频分析整个游戏、改善建模质量，并开始修改代码。本文区分现状证据、设计目标与后续扩展；后文的验收指标是目标，不能当作已经实现的功能。

## 1. 当前判断

开始本轮时，已有实现能够演示起降流程，也通过 29 项仿真测试。但普通玩家主要是在正确时刻点击许可，缺少提前计划、空间调度、选择代价与错误恢复。提高流量会暴露地面死锁，无法直接把“演示”变成“高峰调度游戏”。

保留 TypeScript / React / Three.js 和纯逻辑仿真分层，逐步重构。先把一座机场的全流程做扎实，再增加双跑道和更多机场。建模与玩法同时推进：3D 必须准确表达机位、路线、等待点、跑道和飞机状态。

## 4. 与参考游戏的主要差距

| 领域 | 现状 | 玩家影响 | 改造方向 |
| --- | --- | --- | --- |
| 地面管制 | 推出后自动沿唯一最短路滑出；落地后自动找机位 | 不能通过路线与放行顺序提升效率 | 推出结束、等待滑行许可、路线预览与确认、拥堵原因、改道/让行 |
| 机场拓扑 | 一条双向共用主滑行道，没有边预约和交叉口控制 | 加密后迎头互堵，玩家缺少解法 | 进出场分流、可选路径、路段方向、冲突点与通行预约 |
| 跑道共享 | 单占用 ID + 一张落地许可就长期预留 | 安全但容量粗糙，缺少未来窗口信息 | 分开实际占用、许可与排序意图；先展示可解释窗口，继续保留执行时互锁 |
| 进近排序 | 单入口/单 STAR；列表按距场排序；无等待程序 | 缺少快慢机、合流、插入离场的取舍 | ETA/序号、等待/恢复、重飞恢复、速度及尾流差异 |
| 冲突 | 当前距离判定，没有未来 CPA 警示 | 等到距离不足才知道，难以提前处理 | 预测提示与实际违规分开；显示冲突对象、预计时刻和原因 |
| 席位 | GND/TWR/APP 只是无线电文字标签 | 全流程缺乏职责与移交反馈 | 飞机所属席位、合法移交、席位筛选与待移交提示；辅助模式减少重复操作 |
| 指令反馈 | 指令立即执行，2.5 游戏秒后才播放复诵 | “复诵延迟”并不是执行队列；约 0.42 现实秒，几乎无感 | 明确状态“已下达/执行中/等待条件”；应急指令优先，不把无线电演出变成操作惩罚 |
| 机型与机位 | 有尾流分类、机位尺寸字段，但未用于调度 | 大机小机的决策差别不够 | 性能包线、机位兼容、跟随间隔和占用时间差异 |
| 评分 | 只用架次和违规；`points` 参数被丢弃，复飞不参与评级 | 玩家不知道为何值得重玩 | 安全/完成/延误分项，事件复盘；主动安全复飞不等同操作失败 |
| 教学与节奏 | 静态说明、两个关卡、默认高峰；教学一架落地后等到结束 | 初学者错过关键时机，熟练者缺目标 | 分阶段任务、教学暂停、完成即结算、交通波次与挑战规则 |
| 工作台 | 固定小面板；雷达标签约 7–8px；没有防重叠 | 信息很多却不易判断先处理谁 | 可读雷达、标签避让、状态分层、待办队列、可调整窗口 |
| 3D | 几何拼装模型、屋顶变换错误、贴地/遮挡和机场尺度薄弱 | 场景不可信，也无法帮助理解调度 | 机场结构与尺寸校正、飞机轮廓/材质/起落架、道面标记、导航灯与稳定镜头 |
| 重玩与调试 | 固定表，没有成绩保存、种子入口与指令回放 | 难以挑战更优方案，也难定位偶现堵塞 | 同种子可复现、事件日志、成绩保存；完整回放作为后续独立模块 |

## 5. 产品目标与玩法原则

定位：中文桌面浏览器里的全流程 ATC 调度游戏。玩家负责顺序、许可和冲突处置，飞行员负责飞行、滑行与常规避碰。

每局 8–15 现实分钟作为标准班次的起步目标，教学拆为短任务。暂停始终可用，倍速是节奏工具。高峰目标是同时面对 2–4 个有意义的事项，避免通过几十个重复点击制造忙碌。

应持续出现三类取舍：

1. 进场快机跟着慢机：减速、等待还是改变顺序？
2. 一架进场即将落地、两架离场排队：是否存在足够安全的起飞窗口？
3. 近出口节省跑道占用但滑行路线拥堵：选更远出口还是等待地面疏通？

所有被拒指令必须解释原因；所有等待都要说明等待谁或等待什么条件。系统不通过瞬移和暗中移除飞机“修复”调度失败。

## 6. 具体玩法设计

### 6.1 完整离场链

机位请求 → 批准推出 → 机坪等待滑行许可 → 选择/预览路线 → 批准滑行 → 跑道外等待 → 联系塔台 → 进跑道/起飞许可 → 起飞 → 移交离场。

路线推荐可以降低操作成本，但玩家必须能看清路线、阻塞位置和替代路径。改变推出朝向应匹配机场几何与后续出口，不提供四个效果几乎相同的装饰性按钮。

### 6.2 完整进场链

出现进场请求 → 判断顺序 → 速度/高度/等待 → 截获进近 → 联系塔台 → 落地 → 指定脱离口 → 清空跑道 → 联系地面 → 获得机位与滑入路线 → 到达机位，完成服务。

“落地架次”与“服务完成”分开显示。满机位时先脱离跑道至安全等待位，不能因没有机位永久阻塞跑道。复飞要有明确可恢复路径和提示。

### 6.3 地面安全模型

- 机场图包含道路方向、限速、可通行机型、冲突点和安全等待点。进出场优先分流，保留可形成决策的汇合区。
- 只预约接下来的一段/冲突区，避免一架机锁住整条路线；确定性优先级防饥饿，不依赖 Map 更新顺序。
- 区分主动等待、前机阻塞、路段占用、机位等待和许可未下达。
- 推出冲突在机位区检查；转弯不切过草地，机型尺度参与净空判断。
- 死锁监测产生可执行的改道/让行建议。主动指令未处理可以等待，算法互等不可永久持续。

### 6.4 空中与跑道排序

- 雷达显示进场序号、ETA、短五边、许可状态和下一步需求；列表支持距离与紧急程度排序。
- 先实现等待与恢复、直飞航路点、复飞恢复和不同机型速度边界，再加入更复杂的程序。
- 跑道面板分开“物理占用”“已许可”“计划顺序”。排序拖动只调整意图，不自动越过安全校验。
- 未来窗口用预计进入时间、占用时长与不确定性余量表示。首轮仍保留严格互锁；窗口调度经过压力测试后才允许更复杂的条件许可。
- 游戏间隔是可调参数，不声称等同真实空管规定；预测告警不扣分，实际间隔不足才形成安全事件。

### 6.5 教学、模式与内容

辅助模式自动处理常规移交和推荐滑行；标准模式让玩家下达许可与决定路线。二者共用运动学与安全规则。

建议关卡：

| 关卡 | 新增决策 | 初始验收目标 |
| --- | --- | --- |
| 迎接首航 | 选机、进近、落地 | 新手 3 分钟内首次落地，完成即反馈 |
| 第一架离场 | 推出、滑行、起飞 | 不看说明书完成一架进出场链 |
| 交汇时刻 | 一进一出争用跑道 | 至少两种安全解法，结果可比较 |
| 晨间高峰 | 快慢机、地面排队、出口选择 | 8–15 分钟形成多轮决策；无算法死锁 |
| 重型机波次 | 尾流、大机机位和慢机 | 不同排序造成可解释的延误差异 |
| 黄昏值守 | 灯光、低能见度和保守窗口 | 信息仍可读，视觉环境对操作有明确意义 |

种子挑战和自由练习用于重玩。风变换向、跑道关闭、双跑道机场需等反向程序、占用模型和回归齐备后加入。

### 6.6 评分与复盘

- 安全事件分级；完成量、全流程完成、平均延误和总延误分开统计。
- 选择安全复飞属于处置结果；不能为了刷零复飞评价而鼓励冒险落地。
- 班末列出关键事件、等待原因、未完成航班与损失时间。事件可以定位飞机及相应时刻。
- 同关卡同种子保存最好成绩，玩家能比较排序方案。教学以完成任务为主，不用复杂分数干扰。

## 7. 建模与视觉改造

### 7.1 机场

优先修正实际几何：机库屋顶使用明确宽/高/长的屋顶截面；建筑包围盒不得侵入跑道和滑行道安全区。航站楼拆分主体、玻璃幕墙、屋顶与廊桥；廊桥连接到合理位置，停机位有引导线和编号。

道面区分跑道、主滑行道、联络道、机坪。补齐中心线、边线、等待线、脱离口名称和必要灯光。所有路线与 3D 使用同一机场数据，禁止在渲染层另写一套滑行路径。

### 7.2 飞机

按窄体、宽体、涡桨构建三个参数化轮廓：变截面机身、后掠机翼、垂尾/平尾、发动机、驾驶舱窗、起落架与轮胎。用比例与轮廓提升识别度，避免堆无意义小零件。

机身、玻璃、金属和尾翼材质分开。地面高度包含起落架与轮胎尺寸，禁止机身穿地。空中收轮、地面放轮；涡桨有螺旋桨动画；航灯采用少量共享材质或实例化，避免每灯一个动态光源。

### 7.3 镜头与环境

塔台视角看清跑道和机坪，俯瞰一键覆盖机场，跟机避免钻进建筑。拖动镜头不触发取消选机，跟机目标消失有明确回退。增加昼/黄昏预设、可读道面光照、阴影与曝光；先保证识别，不用强雾或过曝遮盖建模问题。

质量档与低性能模式保留，先测普通笔记本/集显和多飞机场景，再决定细节级别。

## 8. 技术实施与依赖

继续保留纯 sim 与渲染分离。建议拆分：

- `sim/ground.ts`：地面运动、路段通行、阻塞原因。
- `sim/runway.ts`：物理占用、许可、安全校验与时间窗口。
- `sim/sequencing.ts`：ETA、顺序、未来冲突提示。
- `sim/traffic.ts`：航班波次、种子与安全投放。
- `sim/scoring.ts`：结构化事件、延误与结算。
- `views/aircraft-model.ts` / `airport-model.ts`：参数化飞机和机场建模。
- `ui/` 独立地图、雷达、指令栏、航班条、教学和结算组件；避免继续扩大单个 App 文件。

依赖顺序：机场拓扑 → 地面通行 → 手动路线 → 席位/完整流程 → 排序与流量 → 评分/复盘。建模几何修复从第一阶段开始，视觉细化贯穿各阶段。

## 9. 交付阶段与验收

| 阶段 | 可交付内容 | 验收门槛 |
| --- | --- | --- |
| A：可信机场 | 修复屋顶与尺度、改善飞机/机场模型、稳定三个镜头 | 建筑不侵入运行道面；飞机无穿地；所有机位与出口可辨认 |
| B：可调度地面 | 新拓扑、推出/滑行许可、路线预览、阻塞解释和通行预约 | 普通与密集进出场完整服务；连续拥堵实验无不可恢复互等、无重叠/瞬移 |
| C：全流程工作台 | 席位移交、分组航班条、可读雷达、待办与教学 | 真人不读文档完成进离场；任务与飞机信息一致，关键窗口无遮挡 |
| D：排序与挑战 | ETA、等待/恢复、复飞恢复、波次、机型差异 | 同一场景存在不同安全策略，并产生延误差异；预测提示不会误扣分 |

每阶段都要保持可运行版本。先交付单机场完整调度版，不以一轮代码修改宣称已达到参考视频的最终成品品质。

## 10. 验证方法

1. 保留现有 29 项回归，并为许可/移交、道路占用、满机位、复飞恢复、路线替换和机型尺寸增加测试。
2. 构造会车、交叉、队尾堵出口、满位、重型机跟随、取消许可和中途改道等对抗场景。程序死锁与玩家主动等待分别统计。
3. 多种子完整班次压力测试；检查有限坐标、资源最终释放、无永久互等、无机位重复分配、无跑道双重进入。
4. 浏览器验证真实点击流程，而不只用 `fast&bot` 截图。覆盖推荐路线、手动路线、等待/恢复、移交、暂停、重开、结算和历史成绩。
5. 1280×720、1440×900、1920×1080 三档视觉检查；对塔台/俯瞰/跟机、机坪/起飞/落地分别截图。
6. 性能测量明确硬件、画质与飞机数。自动测试无法证明好玩，最终需要至少三名新手试玩和熟练玩家同种子重复挑战，记录首次完成时间、困惑点、无意义等待与重玩意愿。

## 11. 范围与风险控制

先不追真实机场 1:1、真实涂装授权、多语 TTS、多人和完整飞行力学。优先全流程决策与空间可信度。

主要风险是地面系统和机场拓扑相互制约，增加流量会掩盖而非解决这类问题。第二个风险是把移交与指令数量误当可玩性。第三个风险是过早追画面细节，仍留下无法恢复的调度状态。

本计划的成功标准是：玩家看得懂、能够提前计划、不同选择有不同结果、错误有恢复路径，并愿意用更好的方案再玩一次。它需要实现和试玩共同验证。
