## 0. 结论先行

1. **它不是"雷达管制游戏"，是"全席位全流程模拟"。** 玩法重心约一半在地面：推出（选机头朝向）→ 滑行路线规划 → 跑道等待 → 起飞 → SID → 移交；进场反向走完落地 → 选脱离口 → 滑到机位。我们现在的实现只做了"空中那半段"。
2. **它赢在机制编排，不只是画面。** 情境化指令条（按飞机状态给真实管制用语选项）、[席位]→[呼号] 双向无线电记录、浮动窗口工作台——这三样是"像在管制"体验感的来源，且都不需要 1:1 美术。
3. **拟真内容壁垒我们追不了，也不该追。** 1:1 机场设施、真实航司涂装、AI 双语无线电、动态昼夜天气是 Unity 3A 级投入。Web 端的胜负手仍是：零门槛 + 机制不打折的"全流程感"。
4. **当前两个实现（atc-sim / atc-sim2）与它的差距，最大项依次是：地面管制域缺失 > 指令交互形态 > 无线电演出 > 3D 表现。** 3D 表现差距最扎眼，但补起来性价比反而排不到第一。

## 1. 机制拆解（视频证据）

### 1.1 全流程管制链

| 环节 | 它的做法 | 证据 |
|---|---|---|
| 推出 | 批准推出 + **机头朝向选择**（朝南/朝北…），拖车动画，廊桥旁推出 | 实机 00–08s；截图2 电台 "可以推出开车，机头朝南" |
| 滑行路线规划 | 地面雷达窗里**在滑行道图上画路线 + 确认/取消**；卡牌显示路线串（`N_B_A_A14`）；3D 地面出现青色引导箭头 | 宣传片 39–54s「滑行路线规划」；截图3 |
| 滑行管理 | 快速滑行 / 跟在前机后 / 无滑行灯 / 暂停滑行 / 等待滑行 / **穿越跑道** | 实机 28–32s 指令菜单；截图1 指令条 |
| 起飞 | 跑道外等待 → 允许起飞（含风向风速复诵），起飞后高速驶出 | 截图2、实机 46–53s |
| 落地后 | **脱离跑道口选择**（如 B3 高速口）、等待通过、联系地面 | 实机 15–27s 指令菜单 |
| 席位移交 | GND / TWR / APP 三席位，电台里出现「联系塔台 119.05」式频率移交 | 截图1 电台、右下席位切换 |

### 1.2 指令交互形态（关键差异点）

- **情境化指令条**：选中飞机后，底部指令条按其状态给选项——推出中给「批准推出/等待推出/变更跑道」，滑行中给「更改路径/暂停滑行/联系塔台/穿越跑道」，五边给「前机落地后/目视跑道/前方等待」。不是表单输数字。
- 空间类指令（滑行路径、跑道）在雷达窗内点选并弹 确认/取消。
- 选项文案就是管制用语，玩家读选项 = 学术语。

### 1.3 信息与演出

- **无线电记录窗**：`[席位] → [呼号]` 双向逐条记录，含飞行员复诵与频率移交；宣传字幕「多语种无线电通信」（AI 生成 TTS）。
- **飞机卡**：呼号/尾流/机型 + 时刻窗（07:35 > 07:43，计划 vs 实际）+ 状态 + 航线串 + 指定机位 Ramp 与跑道 + 距离/地速/方位/高度。
- **按席位分组的飞机列表**（右下），颜色编码状态。
- **计分牌**：落地数 / 起飞数 / 黄牌 / 红牌（实机 61s 顶部）。
- **天气窗**：当前风 + 预报时刻两组箭头；风变 → **变更跑道**决策（23 ↔ 05）。
- **浮动窗口系统**：所有面板可拖拽/缩放，底部有「进入窗口编辑模式」。

### 1.4 表现层（内容壁垒，仅记录不追赶）

1:1 机场（廊桥/拖车/道面红禁行线/滑行道灯/进近灯/PAPI）、真实航司涂装、落地轮胎烟、昼夜循环（日出雾 → 正午霾 → 晚霞 → 星夜）、城市背景、电影化镜头。

## 2. 我们的两个实现现状

同一份 `ATC-SIM-PLAN.md` 的两个平行实现，**玩法域相同**：都只覆盖空中段（STAR 进场 → 引导 → ILS 落地；跑道外等待 → 起飞 → SID → 出界），均无推出/滑行/穿越等地面管制。

| | atc-sim | atc-sim2 |
|---|---|---|
| 规模 | ~3670 行 | ~4820 行 |
| typecheck | ✅ | ✅ |
| 仿真验证 | `src/dev/headless.ts` 冒烟（2h：19 生成/11 落地/0 坠机） | `scripts/sim-test.ts` **20 项断言测试全 PASS**（运动学/进近/冲突/等待/起飞/NaN/性能） |
| 视图架构 | ViewHost + mount/unmount 切换 | 双视图常驻 + setVisible 切换；塔台视角 OrbitControls 可拖动环视 |
| 3D 场景 | 平面地面 + 2 跑道 + 1 盒子航站楼 + 圆柱塔台；飞机=圆柱+锥+板，按尾流类别涂色 | 有滑行道几何、雾、环境组块，飞机模型略细 |
| UI 形态 | 顶栏 + 固定右侧栏（数字输入+按钮指令面板） | 顶栏 + 侧栏，class 化 UI，指令同为表单式 |
| 无线电呈现 | 系统旁白式事件日志 | 同左（格式不同） |
| 已构建 dist | 无 | 有（node_modules 本机已补装） |

**判定**：两者都没有达到"可对标"的成品形态；差距主要不在两套代码之间，而在共同的缺失域。不建议双线并行维护，应尽快二选一做基干（见 §4）。

## 3. 差距分析（按对体验的影响排序）

| # | 差距 | 层 | 影响 | 补齐成本 |
|---|---|---|---|---|
| 1 | **地面管制域整体缺失**：无推出/滑行路线/穿越跑道/脱离口，GROUND 阶段只是一条 takeoff 指令 | 玩法 | ★★★ 它一半的玩法我们不存在 | 大（需滑行道图数据 + 路径规划 + 指令链），但机制性工作，Web 可做 |
| 2 | **指令是表单，不是情境化指令条**：输数字按按钮 vs 状态驱动的管制用语选项 | UI | ★★★ 决定"像不像在管制" | 中（纯 UI + 状态机映射） |
| 3 | **无线电记录缺演出**：现在是系统旁白（`${callsign}，${describeCommand}`），没有 [席位]→[呼号]、复诵、频率移交 | 演出 | ★★ 成本极低收益高 | 小（sim 已有 lastInstruction，改包装即可） |
| 4 | **无浮动窗口工作台 / 席位分组列表 / 计分牌** | UI | ★★ | 中 |
| 5 | **3D 表现基础薄弱**：无昼夜、无灯光系统（进近灯/边灯/PAPI）、无机坪静态机、飞机是几何拼接体 | 表现 | ★★ 最"扎眼"但非体验核心 | 中（Three.js 灯光+程序化增强，不求 1:1） |
| 6 | 无航班计划感（ETA 窗口 / Ramp 指定 / 时刻表） | 玩法 | ★ | 小（traffic 生成时排班） |
| 7 | 风变已有"跑道构型变更"事件，但无「变更跑道」指令闭环 | 玩法 | ★ | 小 |

## 4. 策略与路线建议

**定位不变**（竞品扫描 §5 的结论依然成立且被视频强化）：不与 Airport Control 27 拼拟真内容；打"Web 零门槛 + 中等拟真 + 全流程感"。**差异化修正一条**：把"全流程感"（含地面段）明确纳入范围——这是它验证过的、玩家要的"真管制"体验核心，且机制层用 Web 完全做得起。

**明确不追**：1:1 机场建模、真实涂装/Workshop、AI 双语 TTS 语音、4K 超宽。

**建议优先级**（体验提升 / 成本比排序）：

1. **P0 · 交互与演出改造**（不新增玩法域，先让空中段"像游戏"）
   - 情境化指令条：按 phase 状态给指令选项，替换数字表单
   - 无线电记录改为 `[席位] → [呼号] + 复诵` 格式
   - 按状态着色的飞机列表 + 顶部落地/起飞/黄牌/红牌计分牌
2. **P1 · 3D 表现层第一次大修**
   - 昼夜循环（天空渐变 + 太阳/月 + 场景曝光）、跑道/滑行道灯光系统、进近灯串
   - 机坪静态停靠机 + 廊桥体块（程序化摆放即可）、雾/天气视觉
3. **P2 · 地面管制域**（最大单项投入，建议在 P0/P1 验证手感后启动）
   - 数据：机场滑行道图（节点+边）、机位表
   - Sim：推出（含朝向）、滑行路径规划与跟随、跑道占用/穿越、脱离口
   - UI：地面雷达窗内画线确认、3D 引导箭头
4. **P3 · 航班计划感**：ETA 窗口、Ramp 分配、变更跑道闭环

**关于双实现的处置**（需要用户决策）：
- 建议**二选一为基干**，把另一套的优点并进去后归档另一套。倾向：以 **atc-sim2 为基干**（20 项断言测试是 plan 文档 §10 明确要求补的资产，且 UI 类化、双视图常驻更省心），把 atc-sim 的 ViewHost 抽象与 headless 冒烟并过来；
- 或以 atc-sim 为基干，把 atc-sim2 的测试脚本移植。两套 sim 层 90% 同源，合并成本不高。
- 无论选哪个：plan 文档 §8 仍停留在"M0 进行中"，与实际（M0–M3 完成）脱节，下一步动工前应先同步。
